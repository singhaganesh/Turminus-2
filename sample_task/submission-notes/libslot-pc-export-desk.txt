Difficulty Explanation
This is not a one file repair for Claude Opus 5 or GPT-5.6. The mill looks like a normal cmake install until you notice four seperate emitters each own a different packaging rule. Shared objects need a real file, a SONAME link and a linker name, plus dependancy names rewritten off the build tree. pkg-config has to follow public versus private cmake edges, not every ELF needed name, and a vendor extra sitting next to the units is a trap. cmake config files have to resolve only from the install prefix. Stamps mix visibility, soversion and the compile token through a documented fold. Hand written JSON dies on the next rebuild.

Solution Explanation
I started with the policy doc and the lattice cmake graph, then ran the mill CLI to see what landed in teh prefix. The so copy path was dropping versioned names. The pc writer was reading needed names and the vendor extra. The cmake writer still pointed at source includes. The ledger used short hashes of unit names. I fixed those four emitters, then ran the mill again so the install tree and ledger were produced together. Private shared deps still had to resolve at consumer link time through SONAME and rpath, not by putting private targets on the public cmake interface.

Verification Explanation
Checks rebuild through the mill CLI before they look at the prefix. They query pkg-config for dynamic versus static library flags and reject the vendor extra. They inspect ELF SONAME strings and the symlink triple. A tiny config mode consumer is configured against the install prefix only and must compile and run. Stamps are recomputed from the documented fold, and a second run of the same token must byte match the ledger plus the pkg-config and cmake files. A second token changes the stamps. Recieve a green run only if the rebuilt tree matches all of that.
