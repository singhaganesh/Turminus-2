Difficulty Explanation
The mill already does the textbook atomic lock replace, and a second run looks healthy, so a frontier agent can close too early. Claude Opus 5 and GPT-5.6 still have to notice that one pin-changing refresh leaves the installed tree on yesterday's pins while the lock and the change report already show today's pins. The report's after column is a false green: it rereads the path, so copying it into the tree would still fail inode and digest checks. A tempting efficiency patch rewinds the still-open descriptor, which only rereads the unlinked old file and changes nothing. The real work is diagnosing handle reuse across four later stages, not inventing a new resolver.

Solution Explanation
I ran one refresh after changing the wanted pins and compared the lock on disk, the installed tree, and the change report. The lock and the report moved; the tree did not. I traced the driver: it snapshots the lock at start, writes a temp lock, renames over the path, then later stages still consume that opening snapshot. Closing the snapshot after the before-digest, then opening the path again for plan, install, and report metadata, made one refresh leave tree, lock, and report in agreement. Rewinding the old descriptor was a dead end. After the source changes I rebuilt and reran the public refresh once.

Verification Explanation
Checks restore a known starting lock, apply a pin change, and run a single refresh. They require the installed versions to equal the lock bytes on disk, the report after fields to equal the tree, and the apply/note inode plus byte encoding to match the replaced lock. They also require the scan-time leftover descriptor field to be zero and replay a second pin channel. Static JSON or a second refresh without a source fix does not pass.
