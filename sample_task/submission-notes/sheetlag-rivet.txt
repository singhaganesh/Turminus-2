Difficulty Explanation
Frontier agents often treat the first mill as a cache warmup because a second mill looks correct and unknown decode is a documented path for frames without decoders. The lag is a process-lifetime intake sheet that discover refreshes on disk after the mill already copied it. Exit status can still look healthy when that copy matches the old decoder set. A shell wrapper that runs mill twice in separate processes is blocked by a per-subprocess mill counter. Held-out descriptions added at grade time still miss after a solve-time double mill. Claude Opus 5 and GPT-5.6 still have to rebuild the binary after editing C; source-only edits leave the shipped mill lagging.

Solution Explanation
The working approach is to watch mill write the ledger, then see emitters follow an older copy of that ledger. Reloading the sheet after discovery, driving emit from that copy, and comparing description files to decoder files for the exit status restores one-pass mill. Rebuild the mill binary so grading runs the repaired program. Ignore the warmup hook that suggests milling twice.

Verification Explanation
Tests restore a seed tree, add descriptions, and run mill once. They check decoder names against description names, ledger stems, KDEC headers, decode JSON for new frames, unknown JSON for nameless frames, and mill exit when the two sets differ. They do not compile the mill for the agent.
